Config & input filters

Model config
The Qwen model's context window is a llama.cpp / --ctx-size property (set at launch), not an ML config option. Analyzer window count is fixed by ANALYTICS_CONTEXT_WINDOWS.
Incremental fine-tuning runs when new labeled windows exist past the watermark (needs ≥ minRows labeled).

Overview

opencode-pi is a local AI gateway on a Raspberry Pi. The opencode agent points its OpenAI-compatible provider at the gateway's /v1 endpoint (localhost:8080 /v1/chat/completions, bearer INFERENCE_API_KEY) and the gateway runs llama-server (llama.cpp) inside its Docker container to serve Qwen2.5-Coder-3B-Instruct (4-bit Q4_K_M, context 32768).
  • Control plane — admin API under /api/* plus the realtime /ws stream; key via x-api-key.
  • Inference plane — OpenAI-compatible /v1/*; key via Authorization: Bearer or x-api-key.
  • Provisioning — scripts/install.sh installs llama-server + the 4-bit model, scripts/update.sh swaps llama.cpp and the model, scripts/cleanup.sh removes old artifacts.
  • Storage — model GGUF lives on NVMe at /opt/qwen-model, mounted into the container at /models. ML artifacts and the warehouse SQLite DB live on NVMe at /opt/qwen-ml (sqlite file analytics.db, persists across docker compose down -v).
  • Analytics — an analytics microservice (Python/FastAPI, container analytics) windows the gateway telemetry every 60s, scores each window against an EWMA reference (Hotelling T² + z-scores), exposes the live scorecard under /api/analytics/*, and auto-trains a TF risk classifier (saved-model → TFLite → live inference on every scored window). Training is gated on new labeled windows past the watermark, so re-training only happens when the distribution drifts.
