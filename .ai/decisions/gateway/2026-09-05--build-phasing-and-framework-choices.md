# Build phasing and framework choices for the gateway

- **Date:** 2026-09-05
- **Decided by:** user
- **Topic:** gateway

## Decision

1. The build proceeds in milestones and stops for review between them: **M0** = container/build
   plumbing (Dockerfiles, compose, lockfile, root scaffold) and **M1** = the control plane
   (auth, status/model/system/metrics/logs API, WebSocket broadcast, placeholder UI). The model
   stack (**M2** — llama-server supervision, `/v1/*` proxy with streaming, and the
   install/update/cleanup scripts) is the next milestone, not part of this one.
2. Until M2 lands, `/v1/*` returns `503` and model update/restart ops return `501` — the control
   plane works without the model runtime present, and M1 is verifiable standalone.
3. All Node tooling runs inside Docker (`node:22-alpine`); npm/tsc/vitest are never run on the
   host. The lockfile is generated by a throwaway container.
4. Development credentials live in a gitignored `.env` (`dev-inference-key` / `dev-admin-key`);
   `.env.example` documents every variable.

## Why

- Verifying the control plane does not need llama-server, the GGUF, or the model volume on the
  Pi — so we get early confidence in the gateway shell (ports, auth, WS, metrics, shutdown)
  before the heavier model stack is layered on.
- Container-only tooling keeps the Pi host clean and makes every environment (dev/test/prod)
  identical; this was the direction set in the project-init decisions.
- Deferring `/v1` keeps M1 small and reviewable; accepting that inference is unreachable until
  M2 is a deliberate, visible trade-off.
